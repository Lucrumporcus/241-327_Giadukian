> Темы: контейнеризация, Docker, Nginx, архитектура информационных систем, прокси, очереди сообщений, мониторинг.

---

## 1. Контейнер, образ, том

**Образ (image)** — это неизменяемый шаблон, содержащий файловую систему, код приложения, библиотеки, зависимости и метаданные (переменные окружения, команду запуска). Образ строится по `Dockerfile` и хранится в реестре (Docker Hub, GitLab Registry).

**Контейнер (container)** — запущенный экземпляр образа. Это изолированный процесс (или группа процессов) со своей файловой системой, сетевым пространством и пространством имён. Контейнер можно запускать, останавливать, удалять; изменения в нём не влияют на образ.

**Том (volume)** — механизм постоянного хранения данных вне жизненного цикла контейнера. Тома управляются Docker, живут отдельно от контейнеров и позволяют сохранять данные (например, БД) между перезапусками.

> **Запомнить:** образ — это чертёж, контейнер — запущенный экземпляр, том — внешний диск для данных.

---

## 2. Чем контейнеризация Docker отличается от виртуализации

| Критерий | Виртуализация (VM) | Контейнеризация (Docker) |
|----------|---------------------|---------------------------|
| Что изолируется | Всё железо + своё ядро | Только процессы, ядро общее с хостом |
| Гостевая ОС | Полная ОС внутри VM | Нет, используется ядро хоста |
| Размер | Гигабайты | Мегабайты |
| Время запуска | Минуты | Секунды (иногда доли секунды) |
| Плотность | Несколько VM на хост | Десятки и сотни контейнеров на хост |
| Изоляция | Более сильная (своё ядро) | Слабее (общее ядро) |

**Суть:** VM эмулирует железо и запускает свою ОС, а контейнер использует **общее ядро хост-системы** и изолируется на уровне процессов через `namespaces` и `cgroups`.

## 3. Технологии изоляции исполняемого кода (минимум 4)

1. **Namespaces** (Linux) — изоляция пространств имён: PID, сеть, монтирование, пользователи.
2. **cgroups** (control groups) — ограничение ресурсов: CPU, память, ввод-вывод.
3. **chroot / pivot_root** — изоляция корневой файловой системы.
4. **seccomp** — фильтрация системных вызовов.
5. **AppArmor / SELinux** — мандатный контроль доступа.
6. **Виртуальные машины** (KVM, Xen) — полная аппаратная виртуализация.
7. **Unikernels** — сборка приложения вместе с минимальным ядром.
8. **WebAssembly** (WASM) — изоляция исполнения в браузере и на сервере.

## 4. Теги образов: `:alpine`, `:slim`, `:trixie` / `:bookworm` / `:bullseye`

| Тег | Базовый образ | Размер | Особенности | Ниши применения |
|-----|---------------|--------|-------------|-----------------|
| `:alpine` | Alpine Linux (musl libc) | ~5–50 МБ | Минимальный, но musl вместо glibc | Микросервисы, лёгкие утилиты, embed-системы |
| `:slim` | Debian/Ubuntu без лишнего | ~70–200 МБ | glibc совместим, убраны лишние пакеты | Production-образы, где важна совместимость |
| `:trixie` / `:bookworm` / `:bullseye` | Debian 13 / 12 / 11 | ~120–300 МБ | Полный Debian, стабильный, все пакеты | Крупные приложения, требующие системных библиотек |

**Разница:**
- **alpine** — минимализм и безопасность, но может ломать пакеты, ожидающие glibc.
- **slim** — компромисс: меньше, чем полный Debian, но совместим с обычными Python/Node-пакетами.
- **trixie/bookworm/bullseye** — это разные версии Debian (по возрастанию: bullseye → bookworm → trixie). Полноценный набор пакетов, но больше по размеру.

## 5. Два способа стартовой инициализации контейнера Postgres

1. **Переменные окружения.** При запуске контейнера передаются `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_HOST_AUTH_METHOD`. Образ `postgres` при первом старте создаёт БД и пользователя автоматически.
2. **SQL-скрипты в `/docker-entrypoint-initdb.d/`.** В каталог монтируются `.sql` или `.sh` файлы — они выполняются один раз при инициализации пустого тома (создание таблиц, пользователей, наполнение данными).

> Дополнительно: `POSTGRES_INITDB_ARGS` для тонкой настройки `initdb`, а также собственный entrypoint-скрипт.

## 6. Преимущества контейнеризации перед развёртыванием на физическом хосте (минимум 3)

1. **Изоляция окружений.** Каждое приложение работает со своими зависимостями, не конфликтуя с другими.
2. **Воспроизводимость.** Один и тот же образ запускается одинаково на любой машине — «работает у меня, работает и у вас».
3. **Плотность и экономия ресурсов.** На одном хосте — десятки контейнеров вместо нескольких VM.
4. **Быстрый старт.** Секунды вместо минут.
5. **Упрощённый CI/CD.** Сборка, тестирование и деплой — через образы.
6. **Версионирование.** Образы тегируются, откаты делать легко.

## 7. Dockerfile: назначение и типы настроек

**Dockerfile** — текстовый файл с инструкциями для сборки образа. Docker читает его сверху вниз и создаёт слои образа.

**Типы настроек (минимум 3):**

1. **Базовый образ** — `FROM python:3.12-slim`.
2. **Переменные окружения** — `ENV PYTHONDONTWRITEBYTECODE=1`.
3. **Установка зависимостей** — `RUN pip install -r requirements.txt`.
4. **Копирование файлов** — `COPY . /app`.
5. **Рабочий каталог** — `WORKDIR /app`.
6. **Открытие портов** — `EXPOSE 8000`.
7. **Команда запуска** — `CMD ["gunicorn", ...]` или `ENTRYPOINT`.
8. **Пользователь** — `USER appuser`.
9. **Тома** — `VOLUME /app/staticfiles`.

---

## 8. docker-compose.yaml: назначение и типы настроек

**docker-compose.yaml** — файл описания многоконтейнерного приложения: сервисы, сети, тома, зависимости. Позволяет одной командой поднять всю инфраструктуру.

**Типы настроек (минимум 5):**

1. **Сервисы** (`services:`) — контейнеры, из которых состоит приложение.
2. **Образ / сборка** — `image:` или `build:` (путь к Dockerfile).
3. **Порты** (`ports:`) — проброс портов хост↔контейнер.
4. **Тома** (`volumes:`) — постоянные данные и монтирование.
5. **Переменные окружения** (`environment:` / `env_file:`) — настройки сервиса.
6. **Зависимости** (`depends_on:`) — порядок запуска контейнеров.
7. **Сети** (`networks:`) — изоляция и связь контейнеров.
8. **Healthcheck** — проверка готовности сервиса.
9. **Secrets** — безопасная передача секретов.
10. **Политики перезапуска** (`restart:`) — `always`, `on-failure` и т.д.

## 9. Почему `requirements.txt` копируется до исходников

**Причина:** Docker строит образ **послойно**, и каждый слой кэшируется. Если сначала скопировать `requirements.txt` и выполнить `RUN pip install`, то слой с зависимостями будет переиспользоваться при изменении кода приложения.

**Что происходит при обновлении кода:**
- Меняется только слой с `COPY . .` — Docker пересобирает его, а слой с `pip install` берёт из кэша.
- Сборка проходит за секунды вместо минут.

**Что достигается:**
- **Скорость сборки** — не переустанавливаются зависимости при каждом изменении кода.
- **Экономия трафика** — пакеты не скачиваются повторно.
- **Оптимальный размер образа** — правильное распределение слоёв.

## 10. Почему не использовать встроенный сервер Django/Flask в production

1. **Один поток, один процесс.** Встроенный сервер (`runserver`, `flask run`) обрабатывает запросы последовательно, не рассчитан на нагрузку.
2. **Отладочный режим.** DEBUG=True раскрывает внутренние данные, трейсбеки, настройки — это дыра в безопасности.
3. **Нет управления воркерами.** Нет автоматического перезапуска упавших процессов, пула воркеров, таймаутов.
4. **Не оптимизирован под статику и медиа.** Отдача файлов через Django — медленно.
5. **Низкая производительность.** Не используется эффективная обработка одновременных соединений.

**Решение:** production-серверы **gunicorn** / **uvicorn** (для ASGI), часто за **Nginx**.

## 11. Как контейнеры обращаются друг к другу

Внутри одной Docker-сети контейнеры обращаются **по имени сервиса** (или по алиасу), которое указано в `docker-compose.yaml`.

**Пример:** backend обращается к БД по адресу `db:5432`, где `db` — имя сервиса в compose.

- **Имя сервиса** (`db`, `backend`, `nginx`) — работает внутри сети Docker.
- **`localhost`** — это сам контейнер, а не хост; использовать его для связи между контейнерами нельзя.
- **IP-адреса** — динамические, использовать их не рекомендуется.

Docker DNS автоматически разрешает имена сервисов во внутренние IP.

## 12. Зачем нужен Nginx помимо gunicorn

**Gunicorn** — сервер приложений, он запускает Python-код, но не умеет эффективно работать с сетью на низком уровне.

**Nginx** — реверс-прокси и веб-сервер. Он стоит перед gunicorn и выполняет:

1. **Отдачу статики и медиа.** CSS, JS, изображения отдаются на порядок быстрее, чем через Django/gunicorn.
2. **Терминацию TLS/HTTPS.** Расшифровка трафика, сертификаты, редиректы с HTTP на HTTPS.
3. **Балансировку нагрузки.** Распределение запросов между несколькими воркерами/серверами.
4. **Кэширование.** Сохранение ответов для повторных запросов.
5. **Безопасность.** Скрывает внутреннюю структуру, ограничивает размеры запросов, фильтрует по IP.
6. **Сжатие (gzip/brotli)** и работа с медленными клиентами (slow loris protection).

**Ключевая идея:** gunicorn — «мозг» приложения, Nginx — «лицо» и «броня» перед ним.

## 13. Архитектура и инфраструктура

**Архитектура** — это структура системы: её компоненты, их свойства и связи между ними. Определяет, **что** и **как** устроено.

**Инфраструктура** — совокупность технических средств, на которых разворачивается и работает система: серверы, сети, хранилища, средства развёртывания и мониторинга. Определяет, **на чём** всё работает.

> **Запомнить:** архитектура — про логику и связи, инфраструктура — про железо и окружение.

---

## 14. Требования к архитектуре информационных систем (минимум 5)

1. **Масштабируемость** — способность выдерживать рост нагрузки.
2. **Надёжность** — устойчивость к сбоям, отказоустойчивость.
3. **Безопасность** — защита данных, аутентификация, авторизация.
4. **Производительность** — низкая задержка, высокая пропускная способность.
5. **Сопровождаемость** — лёгкость внесения изменений.
6. **Расширяемость** — добавление нового функционала без переработки.
7. **Совместимость** — интеграция со сторонними системами.
8. **Наблюдаемость** — логи, метрики, трейсинг.
9. **Экономическая эффективность** — разумные затраты на ресурсы.
10. **Переносимость** — работа в разных окружениях.

## 15. Виды архитектур согласно SEBoK и ISO/IEC/IEEE 42010-2011

**SEBoK** (Systems Engineering Body of Knowledge) выделяет архитектуры:
- **функциональная** — что делает система;
- **логическая** — как компоненты связаны;
- **физическая** — где и на чём развёрнута;
- **продуктовая** — какие артефакты получаются.

**ISO/IEC/IEEE 42010-2011** определяет:
- **архитектурное описание** (architecture description);
- **заинтересованные стороны** (stakeholders);
- **точки зрения** (viewpoints) и **представления** (views);
- **архитектурные решения** (rationale);
- **соответствия** (correspondences).

Формулируется требование описывать архитектуру с разных точек зрения для разных стейкхолдеров (разработчики, DevOps, безопасники, менеджеры).

## 16. Монолитная и микросервисная архитектура

**Монолит** — единое приложение, в котором весь функционал собран в одном процессе и разворачивается как единое целое.

**Микросервисы** — приложение разбито на множество небольших сервисов, каждый из которых решает свою задачу, имеет свою БД и общается с другими по сети (HTTP, gRPC, очереди).

| Критерий | Монолит | Микросервисы |
|----------|---------|--------------|
| Развёртывание | Одним артефактом | Множество независимых сервисов |
| Масштабирование | Вертикальное или всего приложения | Горизонтальное по сервисам |
| Технологии | Один стек | Разные языки/фреймворки на сервис |
| Связность | Внутри процесса | По сети |
| Сложность | Растёт с размером кода | Растёт в инфраструктуре |

**Преимущества монолита:**
1. Простота разработки и отладки на старте.
2. Один деплой, нет сетевых задержек между частями.

**Недостатки монолита:**
1. Сложно масштабировать точечно.
2. Изменения требуют пересборки всего приложения.

**Преимущества микросервисов:**
1. Независимое развёртывание и масштабирование.
2. Технологическая гибкость (каждый сервис на своём стеке).

**Недостатки микросервисов:**
1. Сложная инфраструктура (сеть, мониторинг, трассировка).
2. Трудности с согласованностью данных между сервисами.

## 17. Прокси

**Прокси** — промежуточный сервер, который принимает запросы от клиента и переадресует их другому серверу, возвращая ответ обратно.

**Разновидности:**
- **Прямой (forward proxy)** — стоит на стороне клиента, скрывает клиента от сервера (VPN, корпоративные прокси).
- **Обратный (reverse proxy)** — стоит перед серверами, скрывает серверы от клиента (Nginx, HAProxy, Traefik).
- **Прозрачный** — без изменения запросов.
- **Анонимизирующий** — скрывает IP.
- **Кэширующий** — хранит ответы для повторного использования.
- **Балансирующий** — распределяет нагрузку.

**Пример ПО:** Nginx как reverse proxy, Squid как caching forward proxy, HAProxy как балансировщик, Traefik для динамической маршрутизации в микросервисах.

---

## 18. Балансировщик нагрузки

**Назначение:** распределять входящие запросы между несколькими серверами для повышения доступности, отказоустойчивости и пропускной способности.

**Примеры применения:**
- распределение трафика между репликами backend;
- отказоустойчивость при падении одного узла;
- обслуживание пиковых нагрузок.

**Алгоритмы балансировки (3):**
1. **Round Robin** — по кругу.
2. **Least Connections** — на сервер с наименьшим числом активных соединений.
3. **IP Hash** — один клиент всегда попадает на один и тот же сервер (сессии).
4. **Weighted Round Robin** — с учётом «веса» серверов.

**ПО (3):** Nginx, HAProxy, Traefik, Envoy, AWS ELB.

---

## 19. Кэширующий прокси

**Назначение:** сохранять ответы сервера и отдавать их повторно без обращения к origin-серверу. Уменьшает нагрузку и ускоряет отклик.

**Алгоритмы кэширования (3):**
1. **LRU (Least Recently Used)** — вытесняется самый давно использованный.
2. **LFU (Least Frequently Used)** — самый редко запрашиваемый.
3. **FIFO** — первый пришёл, первый вышел.
4. **TTL-based** — по времени жизни записи.

**Что не следует кэшировать:**
- персональные данные авторизованного пользователя;
- ответы с `Cache-Control: no-store`, `private`;
- POST/PUT/DELETE-запросы;
- динамически меняющийся контент без явных заголовков.

**Настройка:** через заголовки `Cache-Control`, `Expires`, `ETag`, `Vary`.

**ПО (3):** Nginx, Varnish, Squid, Redis (как кэш), CDN (Cloudflare, CloudFront).

## 20. Очереди сообщений

**Сообщение** — единица данных, передаваемая между компонентами системы (JSON, текст, бинарный формат).

**Очередь (структура данных)** — структура «первый пришёл — первый вышел» (FIFO). В контексте систем — буфер для сообщений.

**Асинхронное взаимодействие** — отправитель не ждёт ответа получателя; он кладёт сообщение и продолжает работу.

**Очередь сообщений** — система, обеспечивающая асинхронный обмен сообщениями между сервисами через брокер.

**Компоненты системы очередей:**
1. **Producer (производитель)** — отправляет сообщения.
2. **Broker (брокер)** — хранит и маршрутизирует сообщения.
3. **Queue / Topic** — очередь или канал.
4. **Consumer (потребитель)** — получает и обрабатывает сообщения.
5. **Exchange / Router** — маршрутизация по правилам (в RabbitMQ).

**ПО (3):** RabbitMQ, Apache Kafka, Redis Streams, ActiveMQ, NATS.

---

## 21. Типовые компоненты системы мониторинга

1. **Агенты сбора метрик** — устанавливаются на хосты и приложения (Node Exporter, Telegraf).
2. **Хранилище метрик** — база временных рядов (Prometheus, VictoriaMetrics, InfluxDB).
3. **Визуализация** — дашборды (Grafana, Kibana).
4. **Система алертинга** — оповещения (Alertmanager, Opsgenie).
5. **Сбор логов** — централизованное хранилище (ELK: Elasticsearch + Logstash + Kibana, Loki).
6. **Трассировка** — распределённый трейсинг (Jaeger, Zipkin, OpenTelemetry).
7. **Проверки доступности** — healthcheck, uptime-мониторинг (Uptime Kuma, Blackbox Exporter).

**Примеры ПО (3):** Prometheus + Grafana, Zabbix, Nagios, Datadog, ELK Stack.
